## [Unreleased]

### Fixed — Tools

- **`channel_turb/run_all.sh` no longer rewrites tracked files (#307).** It regenerated `channel.grd`, the STRs and `INPUT/gotm_*.nml` in the case folder, so a benchmark run left tracked files modified. It now writes the grid, the STRs, the namelists and all output into the untracked `run/` folder (`analyse.py` and `profiles.npy` too: run a manual `analyse.py` from there) and ends with a check that the folder's git state is unchanged. No result changes: every output file is byte-identical to the old script's.
- **`shyelab -outformat nc` converts a file with several tracers (#292).** The tracer ids 301, 302, ... were all named `concentration` and NetCDF refused the second define ("name in use"), so a `.conz.shy` file with `iconz > 1` could not be converted. With more than one id in 301..399 (367, the river index, has its own name) each gets the name `concentration_<id-300>` (`concentration_1`, `concentration_2`); a file with one tracer keeps `concentration`. The count is over the variables selected for the conversion, so converting one tracer of a multi-tracer file gives `concentration`. Ids 10 and 367 are both still named `tracer` (a file holding both would still fail). Only the NetCDF writer changes: model results are unchanged. New gate `testcases/examples/mar_menor/check_nc_tracers.sh`.
- **`shyelab -outformat nc` now converts EUTRO and mercury output (#222).** The ulva variables (741, 742) and the mercury variables (251-299) had no name in the NetCDF writer (`src/tools/shynetcdf/netcdf.f90`), NetCDF refused the empty name and `shyelab` left a 32-byte `out.nc` of zeros behind and exited 0. They now have names and units (`ulva_biomass`, `hg0_water`, ...), an id that still has no name gets `var_<id>` and a log line, and a failed NetCDF call removes the unfinished `out.nc` and exits with status 1 (it exited 0). Only the NetCDF writer changes: model results are unchanged. New gate `testcases/examples/weutro_box/check_nc.sh`.

### Fixed — MPI

- **A time or date parameter that `convert_time_d` or `convert_date_d` cannot parse (for example `idtoff = 'xyz'`, or a bad `itanf`) now stops every process with exit 33, and the restart log no longer reads like an `itdrag` mismatch when the file's and the run's `itdrag` are the same (#330).** `convert_time_d` and `convert_date_d` (`outputd.f90`) ended on a bare `stop`: exit 0, and on several processes no MPI abort (`mpirun` exited 1); they now end through `shympi_abort_internal`, naming the parameter (`error stop convert_time_d: cannot parse idtoff`). With the same `itdrag` in the file and the run, neither 3 nor 4 (the default 0), the restart reader logged `windcd not applied (file itdrag = 0, run itdrag = 0)`; it now logs `windcd not applied (itdrag = 0 here and in the file; windcd is restored only with itdrag = 3 or 4)`. No result changes.
- **An allocation failure in `mod_meteo` and in the restart gather/scatter helpers now stops every process (exit 33) (#324).** A bare `stop` ended only the rank that failed and left the others hanging in the next collective; they now end through `shympi_abort_internal`, naming the array. No result changes.
- **The committed `shyparts` snapshots are the METIS partition again (#302).** `MM_coarse.{2,4}` and `venlag62.{2,4,8}` `.elem.grd` (and their `.node.grd`) were written before #290 from an element partition that `check_connections` had damaged (`MM_coarse` on 4: 478 / 549 / 594 / 924 elements per domain, now 637 / 638 / 638 / 632). They are regenerated with the current `shyparts`; `shyfem-ui/tests/test_shyparts_contract.py` pins the new counts, checks the balance of every snapshot and compares one with a fresh run. No model result changes: nothing but that test reads these files.

- **MPI: `setweg(-1)` runs on every process, so wetting and drying start the dry-element counter as in a serial run (#295).** The call that starts the counter `iwetv` of the elements that are dry at the beginning (`shyfem_subs.f90`) was made only in a serial run (`if( .not. bmpi )`, a porting placeholder from 2017). On several processes the first `setweg(0)` counted as a new time, so such an element began at -1 instead of +1, and passed the re-wetting gate (`-iwetv > 5`) one step earlier than serially. The call is per element and sets the same constant on every element, ghosts included, so no exchange is needed. **Results change:** a run on 2 or more processes that has elements dry at the start and hits the re-wetting window (an element of mean depth above `hzon` with one node below it, while only the multi-process gate is open) now equals the serial run byte for byte (`.shy`, `.ext`); before, the dry-element count and the time step split from it at step 5 or 6 (Mar Menor `mm_hyd_12b` without tilt, 15 against 12 dry elements at 00:30; `venlag_smoke` with `zconst = -0.8`; a restart read from a STR that starts before the restart time, see #278). Serial runs, and runs without dry elements at the start, do not change. The new `testcases/examples/mar_menor/check_wetdry_mpi.sh` runs `mm_hyd_12b` without its tilt lines for one day serially and on 2 and 4 processes, requires dry elements at the start of the serial run, and requires the `.shy` and `.ext` files to be byte-identical (it fails on the previous code).

- **`check_partition` gives back the element areas it changed (#290).** `check_connections` checks every domain on the master alone, replacing the basin by the domain (`make_new_basin`) and putting the old one back (`restore_old_basin`); both treated the node areas `iarnv` and the element areas `iarv` as part of the basin, but only `iarnv` was repaired (at the end of `check_connections`), so afterwards the master held other element areas than the other processes (505 of the 2545 elements of Mar Menor on 4 processes) and the partitioner's `epart = iarv` was wrong there. `make_new_basin` now saves both arrays and `restore_old_basin` restores them. **No result of the model changes:** nothing has read the areas since #279; `.shy`, `.rst`, particle files and `partition.*` files of `mm_hyd_00` on 4 processes are byte-identical to before. The standalone tool `shyparts` wrote its `*.elem.grd` from that damaged array, so that file now differs by the 505 elements (MM_coarse, 4 parts), which now carry the METIS element partition; its node partition is unchanged. New test hook `SHYFEM_PARTITION_CHECK` (every process prints how many element areas `check_partition` changed) and `testcases/examples/mar_menor/check_partition_areas.sh`.

- **Mar Menor test cases: a stale `GRID/MM_geo.bas` is found and replaced (#280).** The geographic basin is not tracked and `make init` does not build it, so a tree kept the file it was given. One built before 9abe01a4 (2026-10-16, exact decimal parsing in `shypre`) keeps the old parser's depths: 112 of the 2,545 element depths differ by one unit in the last place (at most 1.9e-6 m; nodes and coordinates are the same bytes), and the cases that read it (`mm_lgr`, `mm_lgr_a`, `c`, `e`, `w`) give other bytes: hydro up to 2.6e-5 in the transports and 1.4e-6 m in the level, 3 to 24 particles beyond 1e-5 degrees at the end. New `check_geo_bas.sh` builds the basin with the `shypre` on `PATH` into a scratch folder and compares it with `GRID/MM_geo.bas`; `check_mpi.sh`, `check_lgr_serial.sh`, `check_lgr_mpi.sh`, `check_lgr_fixes.sh` and `check_itlin.sh` call it first, and a stale file is replaced with one line saying so (`--check-only` fails instead, with the advice `cd GRID && shypre -noopti MM_geo.grd`). A fresh basin prints nothing, so no gate output changes. Note: `check_lgr_serial.sh`, `check_lgr_mpi.sh` and `check_lgr_fixes.sh` now need `shypre` on `PATH` (they did not before); the note names the `shypre` used, a symlinked stale file is not replaced (the check fails with the advice). **No result of the model changes:** only test scripts are touched. Tested by `test_geo_bas.sh`.

- **MPI: `partition.N.elem.grd` is the same file at every run (#279).** At the start of a run on several processes every process wrote the partition files into the same folder at once, and the element partition held by the master was not the one the other processes held (`check_partition` works on the basin of the master and leaves the element areas there different: 478 / 549 / 594 / 924 elements per domain instead of 637 / 638 / 638 / 632), so the file got the content of whichever writer came last: 4 different files in 10 runs of `mm_hyd_00` on 4 processes. The master alone now writes the files, with the element partition of METIS (so the log lines `Grid with partition on ...` appear once, not once per process). The node partition the model uses was always the same and nothing reads these files: no result changes (`.shy`, `.rst`, particle and `.inf` files byte-identical to before). The new `testcases/examples/mar_menor/check_partition_file.sh` runs the case 12 times and requires one md5 for every `partition.*` file.

- **The `sedimt:` lines of the older routine `sedimt` (`icust = 82`, `custom_admin.f90`) are written once, with the totals of the whole basin (#274).** On several processes every process opened the `.inf` file and wrote its own line with the totals of its own domain (ghost nodes included), over each other; now each process sums the nodes it owns, the values are reduced to the global node order and the master adds them and writes the line (as for `issedi = 1`, #220). The `sedimt:` lines on one process are unchanged and those on 2 and 4 processes equal them (576 of 576 lines of the new `check_sedimt_mpi.sh`). Results: no change; the `.shy` files do not change; only the `.inf` and screen lines of `sedimt` on several processes change.
- **A 3D restart file is read on several processes also when a process has fewer vertical levels than the basin (#278).** Such a run stopped at the restart with `restart: vertical structure array size mismatch` (exit code 33): the file holds the layer depths of the whole basin and a full column for every node and element, and `rst_get_vertical` compared the number of layer depths with the levels of the process (Mar Menor with the 19 levels of `mm_hyd_41`: 18 and 19 levels on 2 processes, 7, 15, 16 and 19 on 4, so these reads stopped there; a read in which every process has all the levels of the basin, e.g. the levels `1 2 3 4 5 80` on 2 processes, worked and is unchanged). It now checks the layer depths against those of the whole basin (`hlv_global`), as a serial read does; each process keeps the levels it has of the full columns, as before. `rst_read_vertical` also decided on the levels of the process whether the file holds the vertical structure, so a process with one level of its own in a 3D basin skipped three records; it now decides on those of the basin, as the writer does. A restart file written serially or on any number of processes now reads on any number of processes. The new `testcases/examples/mar_menor/check_rst3d_mpi.sh` writes a 3D GOTM restart (`mm_hyd_41`, 19 levels, and 10 levels from 8 m, where on 4 processes the process in the lagoon has one level) serially and on 4 processes and reads both files serially and on 2 and 4 processes: every read ends, and its `.shy` and `.ext` files are byte-identical to the serial read of the serial file. **Limits:** in a basin with wetting and drying (`venlag_smoke`) a 3D restart read on 2 or 4 processes whose STR starts before the restart time was not byte-identical to the serial read (water level 2.6e-5 m after one hour), also with `flgrst = 0`; the cause was outside the restart reader, the dry-element counter `iwetv` (fixed in #295, see below, after which such reads equal the serial read); a read whose STR starts at the restart time was identical before. Results: no change; the format of the restart file and what is written do not change; the runs that stopped now read the restart.

### Changed — MPI

- **MPI: output and restart files take every node from its owner and every element from its main process; new ghost check `SHYFEM_GHOST_CHECK` (#268).** `shympi_l2g_array`, the gather behind every output and restart file, copied the local values of every process, ghost copies included, in process order, so the copy of the highest process won and a module that left a ghost out of step (simple sediment, #262) showed the ghost's value in the files. It now copies only the own nodes of each process and the elements of which it is the main process (`id_elem(1,ie)`): both come first in the local numbering (`adjust_indices`), which a new start-up check verifies together with every node and element of the mesh being covered once. Since the files no longer show a stale ghost, `SHYFEM_GHOST_CHECK=1` (or `shyfem -mpi_debug`) makes the master compare every ghost copy with the owner's value at every gather and report those that differ, without stopping the run (lines `GHOST CHECK:` with the shy file and variable, the restart file and array number or the debug record, the node or element, both processes and both values; a 3D level array is compared down to the bottom of each node or element, from the owner's `ilhkv`/`ilhv`; the labels of the shy and restart records are made only while the check is on); `check_ssedi_mpi.sh` and `check_mpi_3d.sh` now run their multi-process runs with it and fail on such a line (with the pre-#262 sediment flux restored, the bed sediment of the write case, `.ssed.shy` and the restart record, would now be byte-identical to serial, while the check reports the stale ghosts), and the new `testcases/examples/mar_menor/check_ghost_gather_mpi.sh` tests the gather and the check with the test hook `SHYFEM_GHOST_DESYNC` (every gathered ghost copy changed: all files stay byte-identical, every file is named). `find_elem_id` (triple points) gathers only `id_elem(1,:)`, the part it uses, which is the same on every process. The shy, ext and inf files (and the 2D restart files) of `mm_lgr_a`, `mm_hyd_41` (6 h, without tilting), `venlag_smoke`, `mm_rst_write` and `mm_rst_keps_write` on 2, 4 and 8 processes are byte-identical to 8.6.0, and `check_mpi.sh 4` (checks 1 to 9), `check_ssedi_mpi.sh`, `check_subset_order_mpi.sh`, `check_mpi_venlag.sh` and `check_lgr_serial.sh` (guard and repeat) pass. **3D restart files written on several processes change, but only below the bottom of a node** (values no reader uses (by reading: a restart is read only into a basin with the same bottom levels, and GOTM reads only down to the bottom); a serial run restarted from either file is byte-identical): a restart record holds a full column for every node, and a process sends zeros for the levels it does not have, so the value below the bottom came from the highest process holding the node and now comes from its owner. The measured set is the five GOTM arrays (`mm_hyd_41`, 6 h, and a closed 3D GOTM case: 24, 277 and 240 values per array on 2, 4 and 8 processes, all below the bottom; the water column byte-identical to 8.6.0 and to serial; temperature, salinity and density unchanged there), but it is not a limit: any 3D restart array that is not zero below the bottom changes the same way. `rstinf` comparing two version 19 restart files, one written by 8.6.0 and one by the new code, reports those records as different (`records are different: numv_gotm 277 28040`); a version 20 file (#303, #304) cannot be compared with an 8.6.0 file that way, since `rstinf`'s diff mode compares only files of the same version.

### Added — shyfem-ui

- **Physics > Lagrangian: the particles' random seed (`lgrseed`).** Core 8.6.0 made every random draw of a particle a function of `lgrseed` (default 1), but the parameter catalog did not list it, so the page could neither show nor change it. The Lagrangian panel now has a "Random seed (particles)" field (integer, -2147483647 to 2147483647) that shows the stored value and writes only an edit, and the STR validator reports an out-of-range or non-integer `lgrseed` as an error, as the core stops on it (#259).

### Fixed — Hydrodynamics

- **A run read from a restart file continues as the run that was not interrupted; the restart format is now version 20 (#303, #304).** The restart record lacked state that the next step uses, so a restarted run differed from the continuous run from its first step on: the evaporation `evapv` of the last heat-flux step, the wet/dry counter of the elements `iwetv` (and the time of `setweg`'s last new step), the COARE skin temperature `tws` and warm-layer difference `dtw` (`iheat = 6`), the drag coefficient `windcd` that COARE sets with `itdrag = 4`, and the k-epsilon state `tken`, `eps`, `visv`, `difv` (`iturb = 2`). In `mm_hyd_41` the water level differed by 3.9e-6 m at the first output after the read and GOTM grew that to a salinity difference of 4.9 by 12:00; wet/dry and COARE cases differed by millimetres, k-epsilon by 0.4 m. A version 20 record holds in its hydro block, after `vtlnv`, `iwetv`, `evapv`, the writer's `itdrag`, `windcd`, a heat flag (`qflux3d` ran in the writer), `tws` and `dtw`, and in the turbulence block of a k-epsilon run `tken`, `eps`, `visv` and `difv`; when a version 20 record restores hydro, `setweg`'s clock is set to the start time of the run (a read of an older file, or with a `flgrst` without hydro, keeps the cold start's clock). A reader applies only what fits its own set-up: `windcd` only if the writer's and the reader's `itdrag` are both 4 (with a running heat flux and the file's heat flag set, #323) or both 3, so the reader's `dragco` stays otherwise (a reader with `itdrag = 0`, or one with `itdrag = 4` reading a file written with `itdrag = 0`, which holds the writer's `dragco`); `evapv` only if its `qflux3d` runs (not with `ibarcl = 0`, without heat fluxes, or with T/S from an offline file); `tws` and `dtw` only if its `qflux3d` runs and the file's heat flag is set (`qflux3d` ran in the writer); the k-epsilon state only if it uses k-epsilon too (a GOTM run that reads a k-epsilon file starts GOTM from its own initial state). Version 17, 18 and 19 files are read as before (a version 19 file continues byte for byte as with the previous code). `rstinf` lists and compares the new records and `rst2shy` reads version 20 files; `rstinf`'s diff mode compares only two files of the same version, so an older file against a version 20 file needs `cmp` or a record walk. The checks of `check_restart_fidelity.sh` that compare this build with the previous one (`old_v19`, `tools_v19`) need `REF_BIN_DIR`, a build of the last main commit before version 20, and are skipped without it. **Results change, only for restarted runs and toward the continuous run:** every record of the `.hydro.shy`, `.ts.shy` and `.ext` files of a run read from a restart file now equals the record of the continuous run at the same time (max|d| = 0) in every case of the new `testcases/examples/mar_menor/check_restart_fidelity.sh` (`mm_hyd_41` restarted at 06:00 with and without GOTM, and with `iheat = 6` and `itdrag = 4` restarted at 06:00 and at 12:00; `venlag_smoke` restarted at 03:00 with GOTM serially and on 2 and 4 processes, and with k-epsilon serially and on 4 processes); runs that read no restart file are byte-identical to before, and new `.rst` files are version 20, so a comparison of `.rst` files with older ones differs. Not made exact (not tested): the ice model, waves, the sediment-transport bed, fluid mud, non-hydrostatic runs, `itsplt = 1`, `flgrst` subsets, multi-record restart files and `wrtrst`.
- **Restart version 20, two reader edge cases (#323): `windcd` with `itdrag = 4` is applied only if the file's heat flag is set, and an `idtoff` given as a time span string (`idtoff = '-2s'`) means T/S from the offline file for the restart reader too.** A writer with `itdrag = 4` whose `qflux3d` never ran (`ibarcl = 0`, no heat flux, or T/S from an offline file: heat flag 0) wrote its own `dragco` as `windcd`, and a reader with `itdrag = 4`, a running heat flux and another `dragco` applied it (at the first step, as `meteo_force` runs before `qflux3d`, and on the nodes that stay dry); it now keeps its own `dragco` (log: `windcd not applied (itdrag = 4, file heat flag not set)`). The reader decoded `idtoff` with `dgetpar`, which gives 0 for a string, so a read with `idtoff = '-2s'` (which `handle_offline` decodes to -2, T/S from the file, and so no `qflux3d`) restored `evapv`, `windcd`, `tws` and `dtw`; it now decodes it with `convert_time_d`, as `handle_offline` does. **Results change only for a restarted run in these two edge cases; no other result changes:** runs that read no restart file and every other restart case are byte-identical, and `.rst` files are the same bytes (no format change). `check_restart_fidelity.sh` gets the cases `drag4_noheat_reads_cd4`, `offline_ts_noheat_str` and `clock_itrst_after_start` (the `setweg` clock with an explicit `itrst` one step after the start: the read counts each step once), requires every record of the continuous run from the first record the read run must write (taken from the case's settings, not from the read run's file), checks that `rst2shy` converts every record (`tools`), and writes no `__pycache__` into the source folder; the skip line of a read without hydro names all seven version 20 records.

- **3D runs without turbulence closure (`iturb = 0`) use `vistur` and `diftur` as documented (#248).** `set_eddy` puts them into the vertical viscosity and diffusivity `visv`/`difv`, but `handle_gotm_init`, called at set-up whatever `iturb`, then replaced them by GOTM's initial 1e-6 m²/s (on a restart from a run with GOTM, by that run's last profile, which `iturb = 0` never updates), so they had no effect: a run with `vistur = 1.e-2` or `diftur = 1.e-3` was byte-identical to one without, apart from the particle step made at set-up (`ilagr = 3`), which came before the replacement. With `iturb <= 0` it now leaves them (the GOTM arrays are still set up or read from the restart file). **Results change for every 3D run with `iturb = 0`:** with the defaults (`vistur = diftur = 0`) the effective vertical viscosity of the momentum and diffusivity of temperature, salinity and tracers fall from 2e-6 to 1e-6 m²/s (the molecular `vismol`/`difmol` alone), that of the Lagrangian vertical random walk (`ilagr = 3`, which adds a fixed 1e-6/3 instead of `difmol`) from 1.33e-6 to 3.3e-7, and the vertical mixing of suspended sediment (`isedi > 0`: `sedim_admin.f90` fixes `dtype = 2`, Van Rijn's factor `bet` of 1 to 1.5 times `visv`, plus `difmol`) from (1 + `bet`)·1e-6, 2e-6 to 2.5e-6, to 1e-6, and with `vistur` set it is `bet`·`vistur` + `difmol`: the sediment follows `vistur`, not `diftur`; the four uses without a molecular term go from 1e-6 to 0: the vertical velocity of the non-hydrostatic model, the stability index of the scalar transport (where the vertical diffusion counts only with `adpar` < 1, default 1), the vertical viscosity and diffusivity columns of the box file (3D box runs; 2D runs do not write them) and the turbulence records of the offline file (3D runs only, too); values set in `vistur`/`diftur` now take effect; and a restart from a GOTM run into `iturb = 0` no longer freezes GOTM's last profile. In the test cases: `mm_lgr_c` (2 days) velocities by up to 3.24e-2 m/s (u; v 2.14e-2), the water level by 1.15e-4 m and particles by up to 3.7e-2 degrees, `mm_hyd_41` with `iturb = 0` (6 h) salinity by up to 0.21 psu (RMS 8e-3), the weutro 3D cases (phytoplankton of `eco_3d_settle` by up to 0.13 of 1.65; its gates still pass). `iturb = 1, 2, 3` runs and 2D result files are byte-identical (debug outputs that record `visv`/`difv`, `-debout` and the Lagrangian debug node file at `levdbg = 3`, change in 2D too: there the values go from 1e-6 to `vistur`/`diftur`). The position floor of case C in `testcases/examples/mar_menor/check_lgr_mpi.sh` was measured again: 19 / 7.12e-3 / 0 to 25 / 3.91e-4 / 0 (log `docs/reviews/evidence/2026-11-lagrange-mpi/floors_vistur248.log`). Mode `vdiff-dt` of `check_lgr_fixes.sh` now has its `diftur = 1.e-3` for the whole run (before, only in the particle step made at set-up). The new `testcases/examples/mar_menor/check_vistur.sh` checks that `vistur` and `diftur` act with `iturb = 0` and that GOTM ignores them.
- **k-epsilon and Munk–Anderson start the first time step from their own vertical mixing (#283, part (2)).** The closure first runs in `turb_closure`, after `hydro` and `run_scalar` of step 1, so step 1 used the `visv`/`difv` that `handle_gotm_init` set at set-up, which for `iturb = 2` and `3` were GOTM's arrays: its initial 1e-6 m²/s (on a restart from a GOTM run, GOTM's last profile read from the file; only GOTM runs write those arrays into the restart file). `handle_gotm_init` now sets them from the closure itself: k-epsilon's initial state (`keps_init`: `visv` 1.3e-6, `difv` 1.1e-9, the constants that `keps_shell` sets again on its first call) and Munk–Anderson evaluated on the initial or restart state (`munk_anderson_shell`; at rest it gives `vistur`/`diftur`). This only initialises and adds no closure step. **Results change for every 3D run with `iturb = 2` or `3`**, cold starts and restarts alike, Munk–Anderson with the default `vistur = diftur = 0` too (its step 1 goes from 1e-6 to 0). **Munk–Anderson:** step 1 now uses the configured `vistur`/`diftur` instead of 1e-6 (with `vistur = 1.e-2`, 10⁴ times more mixing), and the effect stays above the size of a 1e-5 °C change of the initial temperature for about a day: in Mar Menor 3D (`mm_hyd_41` without tilt, `vistur = 1.e-2`, `diftur = 1.e-3`, 5 days, output every 3 h) salinity differs at the first output (3 h) by up to 4.9 (RMS 0.073, against 2.3e-5 for the 1e-5 °C twin; u by up to 3.1e-3 m/s, RMS 1.7e-4 against 1.6e-5); through 24 h its RMS stays between 7.7e-4 and 0.080, 2.5 to 3000 times the twin's (24 h: 0.046 against 5.3e-5); from 27 h on it is of the twin's size or smaller at every 3-hourly output but one (75 h: 3.0e-3 against 2.5e-4; 120 h: salinity RMS 1.4e-4 and u RMS 1.8e-5, against 1.9e-4 and 1.7e-5). ### Changed
- **MPI: the scalar transport adds the element contributions at a node in the serial order on several processes (#263).** `conz3d_omp` adds the contributions of the elements around a node colour by colour (the independent element subsets of `subset.f90`, made for OpenMP), and every process coloured its own part of the mesh, so a node got its elements in another order than in a serial run. The double-precision sums then differed in the last bits at every step; cast to single precision they nearly always gave the serial value, but now and then a salinity or temperature rounded to the next value and the difference spread. On 4 processes `venlag_assim` is now byte-identical to serial (`.hydro.shy`, `.ts.shy`, `.ext`); the new test `testcases/examples/mar_menor/check_mpi_venlag.sh` requires that. - **Particles: the vertical random walk takes its time step from the curvature of the diffusivity (#257).** `lag_vdiff_ele` sets the time step of the vertical random walk (`ilagr = 3`) in each element from the curvature K'' of the diffusivity: Visser (1997) requires the step to be much smaller than min 1/|K''| over the water column, and the code takes 1/100 of that, 1/(100 max|K''|). It computed its "second derivative" as (K(l+1) + 2 K(l) + K(l-1))/hl(l)^2, about 4 K/h^2, a sum instead of a curvature: the step was about h^2/(400 K) even for a diffusivity constant over depth. It is now the second difference over the interfaces l-1, l, l+1 with their own spacings hl(l) and hl(l+1) (exact for a quadratic profile, (K(l+1) - 2 K(l) + K(l-1))/h^2 for equal layers), in a routine of its own (`lgr_vdiff_curvature`) that `check_lgr_fixes.sh vdiff-dt` compiles and tests on unequal layers (a sign fix alone, with one spacing, fails that test); an element with a layer of zero thickness takes the smallest step, 2 s. In `mm_hyd_41` with `ilagr = 3` (one day) the mean step goes from 24.9 s to 33.5 s and the sub-steps per 300 s step from 98.4 to 41.7; the element steps that would need more than the 100 sub-steps `diff_body` allows (it stops there, so the particle diffuses for less than the step) from 396008 to 66071 of 735505. With a diffusivity constant over depth the step is now the model step everywhere (new mode `check_lgr_fixes.sh vdiff-dt`); the end of an `ilagr = 3` run writes a new log line with these numbers. **Results change for every run with `ilagr = 3`** (serial only: it stops on several processes); no other run changes.

In a continuous release along the open boundary nodes 85 to 99 (`lgrpps = 0.01`) 77 of the 219 particles started in an element that does not hold their side; now none does (new mode `check_lgr_fixes.sh segments`). **Results change for continuous releases at a level or flux boundary (`lgrpps` other than 0 with `ibtyp` 1 or 2: the release element, and with `lgrpps` below 0 the boundary flux that sets the number of particles; serial only, `lgrpps` stops on several processes) and for shyplot's vertical sections along a line (the element, and so the depth, chosen for each segment)**; no other run changes. Note: the open-boundary node list of the Mar Menor cases skips the boundary nodes 13 and 14 (its segments 99-100 and 162-163 are sides inside the mesh), so a release along the whole of it still stopped with `create_parts: error in boundary`, until #254 (below), which skips those two pairs with a warning.
- **Particles: a release point outside the mesh releases nothing instead of a particle without an element (#247).** `insert_particle` inserted a particle with element 0 when no element held the release point, and the next output read the geometry of element 0: in `mm_lgr_a` (2D) and `mm_lgr_c` (3D) with a trajectory release (`lgrtrj`) whose first point lies east of the basin the run stopped at the first output after it, with SIGSEGV and SIGFPE. `insert_particle_3d` and `insert_particle` now release nothing for such a point (before they read the layers of an element or take a slot and an id), count the particles it would have released, and the trajectory release writes one line per point with the count (`particles not released, point outside the mesh: N`; its `new particles released` line now gives the particles actually released, not the planned number). The skipped particles take no id, so the particles released later keep the ids 1, 2, ...; on several processes no release passes a point without its element (`lgrtrj` stops at start-up), so their ids are unchanged. New mode `check_lgr_fixes.sh outside`. **Only runs that release at a point outside the mesh change** (today only possible with `lgrtrj`, serial only; such a run crashed before); no other run changes.
- **Particles: decay follows its e-folding time whatever the time step (#246).** `lagrange_decay` tested every particle at every time step against the survival of its whole age, exp(-age/`ldecay`), with a new random number each step, so the survival after a time t was about exp(-t^2/(2 `ldecay` dt)): in `mm_lgr_a` with `ldecay = 86400.` (one day) and a 300 s step all 145 particles had decayed after five hours. A particle now decays in a step with the probability 1 - exp(-dt/`ldecay`) (dt the part of the step since its release), one draw of its own stream per step (site decay, in double precision: the probability of a step can lie below what a single precision draw resolves), so it survives a time t with the probability exp(-t/`ldecay`): in `mm_lgr_a` 2 of the 145 particles are left after the four days (2.7 expected), and with about 5000 particles and `ldecay` of six hours the survivors of runs with 300 s and 60 s steps are within 2.2 standard deviations of exp(-t/`ldecay`) at every hourly output (new mode `check_lgr_fixes.sh decay-rate`). A run restarted from its particle file (`lgrini`) decays as the run that went on, although the file resets a particle's age (the first call after the restart is at the restart time, the next steps are full steps with the same draws): with `ldecay = 3600` and a restart after one hour the active particles of all 60 outputs are those of the run that went on, the 5 that decay in the first step after the restart among them (`decay-rate`, part 2). **The particle results of every run with `ldecay` above 0 change** (serial runs only: `ldecay` stops at start-up on several processes); no other run changes.
- **Particles: runs with random draws are repeatable, on any number of threads and processes (#225).** The particle module drew its random numbers from the compiler's `random_number`, which the model never seeded (gfortran starts it differently in every run, and each OpenMP thread drew in the order it reached the draws), and from `ggrand`, one saved stream shared by all threads, so two serial runs of the random-walk case `mm_lgr` (`rwhpar = 0.5`) wrote different particle files, and a run on several processes could not be compared with the serial one. Every draw of a particle now comes from its own stream: a counter-based generator (Threefry-4x32-20 of Salmon et al. 2011, integer arithmetic on 32-bit words that never overflows) computes it from a seed, the particle's id, the absolute time of the time step and the kind of draw (horizontal and vertical random walk, beaching, random depth at release, sediment class and deposition, decay, larvae; the draws of a continuous release that belong to no particle come from a stream of the step). The seed is the new parameter `lgrseed` of `$lagrg` (an integer, default 1). Two runs of `mm_lgr` are now byte-identical, so are runs with 1 and 4 OpenMP threads (serially and on 4 processes); a run restarted from its particle file (`lgrini`) and restart file writes, after the restart, the records of the run that went on, also when it releases particles after the restart: those now get the ids the run that went on gives them (the counter of ids stayed at 0 after reading the file, so a release gave the ids 1, 2, ... again and two particles drew the same numbers); the one exception is the side a particle takes when it lands exactly on a mesh vertex, which still counts the time steps of the run and can differ after a restart; and on 2, 4 and 8 processes `mm_lgr` is compared with the serial run like the other particle cases (its row of position floors in `check_lgr_mpi.sh` is 0 particles beyond 1e-5 degrees and a largest distance of 0, set by the owner on 2026-11-23: with the multi-process hydrodynamics byte-identical to serial (#230, #238), the particle positions of 2, 4 and 8 processes equal the serial ones exactly). **The particle results of every run with random draws change once** (a random walk with `rwhpar` other than 0, `ilagr = 3`, beaching, `ipvert` below -1, sediment, decay, larvae, continuous release); runs without random draws are unchanged (the five Mar Menor cases with `rwhpar = 0` are byte-identical to the build before). New tests: `check_lgr_random.sh` (the generator: the Random123 test vectors, statistics of 10^6 draws along each key, an independent Python implementation, the undefined-behaviour sanitizer), `check_lgr_fixes.sh seed`, and `mm_lgr` in `check_lgr_serial.sh repro`.
- **Particles under MPI: a hand-over list that cannot grow stops the run from the main thread (#242).** The lists of particles marked for the hand-over and of parked particles grow inside the OpenMP particle loop; when the larger list could not be allocated, the thread that held the critical section called `MPI_ABORT` itself, although MPI is initialised with `MPI_THREAD_FUNNELED` (only the main thread may call MPI). The failure, and the two argument checks of the same routines, are now recorded and the particle is left out of the step; the main thread stops the run with the same message right after the loop and before every collective call of the hand-over, with a line `lgr_mpi_list_check:` that names the list, the sizes and the thread that found it. A run that works is unchanged; the new test hook `LGR_TEST_GROW_FAIL=export|park` exercises the path, and the growth itself was checked on 4 processes with 4 threads against 1 thread (identical particle files).
- **Particles: an internal-error guard of the tracker hit inside the OpenMP particle loop stops the run from the main thread, and the guards of the serial-only steps there exit with code 33 (#256).** The guards of the particle tracker that fire only on a programming error or a corrupt state (`track_single`, `track_xi`, `track_xi_next_element`, `track_xi_get_vertical`, `track_xi_check`, `lagr_layer_thickness`, `diff_body`) called `MPI_ABORT` themselves; inside the particle loop of `drogue` run by several OpenMP threads that can be a worker thread, which MPI (initialised `MPI_THREAD_FUNNELED`) does not allow. The guards of the serial-only steps in that loop (`lgr_diff_vert` and `diff_get_vert` of the vertical diffusion with `ilagr = 3`, `lagr_count` and `lagr_connect_count` of the connectivity) ended with a bare `stop`, which exits with code 0. Inside the loop on several threads a guard now records its message (the mechanism of #242, generalised by a kind and the message) and leaves its particle with defined values, the tracker stops and the remaining particles of the loop are skipped, and the main thread stops the run after the loop through `shympi_abort_internal` with the guard's message (exit code 33); outside that loop (release, hand-over), and in a loop run by one thread, a guard aborts at once as before. The warning counters of the advection and diffusion steps and the counts of the connectivity, written by all threads, are OpenMP atomic. A run that works is unchanged. Check: `testcases/examples/mar_menor/check_lgr_fixes.sh int-fail` (test hook `LGR_TEST_INTERNAL_FAIL=1`: on 4 processes with 4 threads the guard of `track_single` fires on a worker thread and the run stops with its message, exit code 33, from the check after the loop; with 1 thread it stops in the guard).
- **Particles: the continuous release along an open boundary runs; two consecutive nodes of the boundary that are not the ends of a side of the basin boundary are skipped with a warning (#254).** A release with `lgrpps` on a level or flux boundary stopped on the sea boundary of the Mar Menor test cases with `error stop create_parts: error in boundary`, a bare `stop` that exits with code 0. That list leaves out the boundary nodes 13 and 14, so two of its 92 pairs of consecutive nodes (99-100, 162-163) are inner sides of the mesh, which the release's check rejected; and `find_elems_to_segment`, which the release asked for the element of each pair, read the element list of the wrong node (#252, above) and gave every pair the element of the next one, so the particles released before that stop started in an element that does not hold their point. The release now counts the elements `find_elems_to_segment` (fixed by #252) gives for a pair (one at a side of the basin boundary, two at an inner side, none if no side joins the nodes), releases on the 90 sides of the basin boundary and skips the two other pairs with a warning at the first release (the hydrodynamics runs with this list, as the Mar Menor cases do, so it is not rejected); for `lgrpps` above 0 their distance is left out of the length the release is spread over. The release per volume of inflow (`lgrpps` below 0) takes the flux over the side between the two nodes whichever way the list runs; **results change** for runs with `lgrpps` below 0 on a boundary list that runs clockwise, where the inflow was taken over an inner side of the element. Check: `testcases/examples/mar_menor/check_lgr_fixes.sh bnd-release` (release by length and per volume of inflow along that list, and a list with no boundary side).
- **Particles: a serial run with `ilagr = 3` no longer stops in its first particle step, and the vertical diffusivity is interpolated down to the bottom (#231).** The Mar Menor 3D case `mm_hyd_41` with `ilagr = 3` stopped with a floating-point exception. All interfaces down to the bottom are now used, so one-layer elements no longer read outside the arrays and no diffusivity in the case is negative (a negative value would be taken as zero and counted in the log line `lgr vertical diffusion: negative diffusivities set to 0`, written at the end of an `ilagr = 3` run); the case runs to the end. Results of `ilagr = 3` runs change for particles in the bottom layer, where the diffusivity was extrapolated from the two interfaces above. Runs with `ilagr` 1 or 2 are unchanged. On several processes `ilagr = 3` still stops at start-up (#228).
- **Particles: decay works in a serial run (#226).** With `ldecay` above 0 a decayed particle got element 0, and the next output read the coordinates of element 0: the Mar Menor case `mm_lgr_a` with `ldecay = 86400.` stopped with SIGSEGV at the first output after a decay. Runs without decay are unchanged; on several processes `ldecay` still stops at start-up (#228).
- **MPI: the particle side fluxes and the flux sections are the serial ones on several processes (#238).** Both walk the ring of elements around a node and add or difference along it (`make_fluxes_2d` for the particle tracker, `flx3d` and `flux_with_bounds` for the flux sections), so their rounding depends on the element the ring starts at. Serial runs are unchanged. On 2, 4 and 8 processes the side fluxes of the five particle cases at the 10 h dump, the particles at every hourly output of the debug dump (both groups of the hand-over check at distance 0 in all 15 runs) and the flux-section file are now byte-identical to serial. The flux mode of `check_lgr_mpi.sh` compares with `--tol 0` (its old relative limit of 1e-5 hid this), and the new `testcases/examples/mar_menor/check_flux_sections_mpi.sh` compares the flux file of 129 sections through the nodes concerned.
- **MPI: the start-up water level of nodes that are dry is the serial one on several processes (#230).** `setznv` gives a node whose elements are all dry the area-weighted mean level of those elements, and on several processes the elements shared between processes counted twice at the nodes along the domain edges (the same defect as `uvtopr`, below). The same correction is made in `bnstress`, whose bottom stress only the `levdbg >= 2` check reads.

- **MPI: 3D runs with GOTM or k-epsilon give the serial result on several processes (#230).** The turbulence schemes take their shear from the nodal velocities of `uvtopr`, which average the velocities of the elements around each node. On several processes the owner of a node already adds all of them, in the serial order, but the exchange then added the partial sums of the other processes that hold the node, so elements shared by two or three processes counted two or three times at the nodes along the edges of the domains. A 3D run with `iturb = 1` or `2` therefore differed from the serial run, by about 1e-2 m/s of current in a closed basin on 4 processes, and by up to 5.9 psu of salinity at the deep nodes behind the open boundary of the Mar Menor 3D case (`mm_hyd_41` without tilting), while `iturb = 0` gave the serial result. On a node partition the processes now take the owner's sums. Serial runs are unchanged. In the Mar Menor 3D cases (open boundary with GOTM, closed basin with GOTM and with k-epsilon) the files `.hydro.shy` and `.ts.shy` of 2 and 4 processes are now byte-identical to the serial ones; the new test `testcases/examples/mar_menor/check_mpi_3d.sh` requires that.
- **MPI: every process classifies the nodes as a serial run does (#238).** `setnod` decides from the sum of the angles of a node's elements whether the node is inner, on the boundary or out of the system. On several processes every process added all the elements it holds, and the exchange then added the partial sums of the other processes on top, so an element held by two or three processes was counted two or three times and a boundary node next to the edge of a domain could pass 360 degrees and be treated as an inner node. With the METIS partition of the Mar Menor mesh this hit 4 boundary nodes on 2 processes, 5 on 4 and 6 on 8 (one of them a node that borders an element set dry at start-up), and a hand-written 4-process partition that cuts through the elements at the open boundary stopped at start-up with `error stop setnod: open boundary node`. Only the main owner of an element now adds its angles. Serial runs are unchanged; runs on several processes change where a node was misclassified. In the five Mar Menor particle cases (`mm_lgr_a`, `_b`, `_c`, `_e`, `_w`: 2D geographic, 2D Cartesian with an open boundary and a river, 3D) the hydrodynamic output file of 2, 4 and 8 processes is now byte-identical to the serial one; before the fix it differed in all 15 runs, so the difference of about 1e-7 relative that #217 found in the multi-process hydrodynamics of these cases was this defect. The particle positions on several processes come closer to the serial ones in most runs (case A on 4 processes: 1 particle beyond 1e-5 degrees at the last output instead of 24; case `w` on 4: 3 instead of 8, but a largest distance of 1.0e-3 instead of 3.3e-4 degrees), all within the floors. The new test `testcases/examples/mar_menor/check_setnod_mpi.sh` compares the class and the angle sum of every node on every process with the serial run (METIS on 2, 4 and 8 processes, two hand-written partitions on 4), through a debug dump of `setnod` that the environment variable `SHYFEM_SETNOD_DUMP` switches on.
- **Semi-Lagrangian advection of momentum (`itlin = 1`) runs in serial 2D runs on Cartesian grids, and stops at start-up everywhere else (#227).** With `ilin = 0` and `itlin = 1` a run died with a segmentation fault at its first time step, serially and under MPI: the back-tracking used side lengths, fluxes and the particle array that the particle module allocates only in a particle run, and with those allocated it stopped at once, because the side tests added in 2015 for the tracker's vertical weights (one of them with a typo, `itrx` for `itry`) turned the tracer's element number negative. The back-tracking now allocates what it uses, keeps its own position instead of writing into the first `nel` particles of a particle run, computes the vertical weights without touching the element number, no longer reads the side table with an element number of 0 or below, no longer gives a tracer that leaves through an open boundary the velocity of element 1, no longer divides by zero on an exactly horizontal side, and no longer prints a debug line per tracer and step. There is no reference for its results; serially the Cartesian 2D Mar Menor cases end with plausible values (`mm_hyd_22a` with `itlin = 1`: largest water level 0.18 m, largest speed 0.66 m/s; the same case with `itlin = 0` has local spikes of 1.97 m and 9.9 m/s). Runs the back-tracking cannot serve now stop before their first time step with `option itlin = 1 (semi-Lagrangian advection of momentum) is not supported ...` and one line of advice: on several processes (`with MPI`; the tracer stops at the edge of a process's domain: on 2 and 4 processes the water level differed from the serial run by 0.05 m in `mm_hyd_22a` without its boundary tilt, 3e-6 m with `ilin = 1`, and by 0.03 to 0.04 m in a wind-driven variant of `mm_hyd_02`, 7e-5 m with `ilin = 1`), on a geographic grid (`on a geographic (lat/lon) grid`; the tracker compares metres with degrees: the Mar Menor geographic basin crashed, and with the division by zero avoided gave 708,358 loop-limit messages in 4 days) and with more than one layer (`in 3D (more than one layer)`; only the first layer gets the term, built from the whole depth: `mm_hyd_43` blew up within three time steps). With `ilin = 1`, where `itlin` is not used, nothing changes. An unknown `itlin` and the eight layer-change checks of the old tracker now end every process through `shympi_abort_internal` instead of a bare `stop`. Test: `testcases/examples/mar_menor/check_itlin.sh`.
- **Particles: decay works in a serial run (#226).** With `ldecay` above 0 a decayed particle got element 0, and the next output read the coordinates of element 0: the Mar Menor case `mm_lgr_a` with `ldecay = 86400.` stopped with SIGSEGV at the first output after a decay. A decayed particle (and one removed by `delete_particle`) now keeps its last element with a negative sign, as a particle that left the basin, and is written in the exited block at its last position at every output; in that case all 145 released particles decay within five hours, each stays at a fixed position inside the basin, and the records of the particles still active are identical to the run without decay. The decay itself is unchanged: it tests every particle at every time step against exp(-age/`ldecay`), so how fast particles decay depends on the time step too (with `idt = 300` and `ldecay = 86400`, a fifth have decayed after one hour). In the particle file a decayed particle now looks like one that left the basin (no reader told them apart, and element 0 was never written). Runs without decay are unchanged; on several processes `ldecay` still stops at start-up (#228).
- **Particles: a line of the release polygon file that is not a point stops the run (#217, after the review of #241).** A comment, a footer line or a non-integer flag in the file named by `lgrlin` used to end the list of polygons silently, so the polygons after it were not released. The run now stops with a message naming the file and the polygon, serially as on several processes; a valid file gives the same release as before. Also from that review: the particle test drivers fail a run that exits with an error, times out or does not launch, the stops check accepts only the abort's exit code 33, and on several processes the hand-over lists start at 1,024 entries and grow, instead of reserving room for the global particle limit on every process.
- **Particles under MPI: options without a multi-process test stop at start-up, and CI checks the particle file on 4 processes (#217, stage 7).** On more than one process a run that sets `ilagr = 3`, `lbeach`, `artype`, `ldecay`, `lgrini`, `ised`, `ilarv`, `icnn`, `lgrpps`, `lgrtrj`, a negative `rwhpar` (diffusivity from the local diffusivity) or an `ipvert` below -1 (random vertical release) now stops before its first time step: rank 0 prints `Lagrangian option NAME is not supported with MPI` and `run on one process, or remove NAME` once, and every process ends with a non-zero exit. Before, `ilagr = 3` and `icnn` already stopped with another wording, four of them ran to the end with tracks nobody had tested, `ldecay` and `lgrini` crashed, and `lgrpps` and `lgrtrj` wrote a particle file before they failed. On one process the options run as before (`ilagr = 3` and `ldecay` crashed there; both now run, see the #231 and #226 entries above). The `$lagrg` parameter texts and `MANUAL.md` list the options; #228 tracks what each needs before it can work on several processes. The MPI gate of the Fortran CI (`testcases/examples/mar_menor/check_mpi.sh`, run by the MPI job on 4 processes) has a fifth check. It runs case `mm_lgr_w`, whose one release polygon covers the whole basin so that the release is split between processes whatever the partitioner does, serially and on the gate's processes. The particle files must have the same ids in the same blocks at every output, and positions within the floors measured on the serial reference; the ids comparison runs with the per-step consistency check on (`levdbg = 2`), and a hand-over check on the debug dump requires that particles which change process stay where the serial run has them, with at least one such particle. The check builds the geographic basin it needs, because `make init` does not, and adds about 30 s to the job on the development machine (the whole gate took 37 s on 2 and 36 s on 4 processes, against 28 s and 25 s with the first form of the check, `pos` and `ids` alone). The measured result of every acceptance criterion of the work is in `docs/reviews/2026-11-lagrange-mpi-acceptance.md`.
- **Particles under MPI: the random walk and the Stokes drift run through the particle file on several processes (#217, stage 6).** The random-walk case keeps the serial ids and counts at every output on 2, 4 and 8 processes, and a new test case releases particles from one polygon around the whole basin, so that a release split between processes is tested whatever the partition. A run that hands a partition to the model through the basin file now also shows particles leaving through the open boundary from an element owned by another process.
- **Particles under MPI: the particle file is written on several processes (#217, stage 5).** A run on more than one process wrote no particle records. Each process now prepares the records of its own particles, the process that released a particle keeps its release record until the next output, and rank 0 writes the file in the serial layout: the same particles with the same ids in the same blocks at every output, global element numbers, positions within what a relative 1e-5 change of the wind drag produces in a serial run. A run on one process writes a byte-identical file. The stray `fort.20` and `fort.22` files of MPI particle runs are gone (every process wrote the file header).
- **Particles under MPI: a particle that crosses the edge of a process's domain continues on the next process (#217, stage 3).** Until now a particle that reached a side between two processes was counted as having left the basin. It is now handed to the process that holds the element across, with its whole record, in mid-step, and finishes its step there exactly as in a serial run. A particle whose step-end position (after the single-precision round trip of the diffusion and Stokes steps) lies in an element its process does not hold is resolved collectively, with the serial search order, and continues on the process that holds the element a serial run finds. The release is identical to a serial run, every particle gets its serial id, and on 2 to 8 processes the closed basins keep every particle and the open-boundary case loses the same particles at the same outputs as serially. Positions differ from serial at the level a relative 1e-5 change of the wind drag produces in a serial run (the multi-process hydrodynamics differs from the serial one by about 1e-7 relative). At `levdbg >= 2` a per-step check aborts the run if a particle is lost or duplicated. Output of particles, connectivity, `ilagr = 3`, and releases from points, boundaries, a trajectory file or a particle file are not yet supported on several processes.
- **Particles: the fallback for a failed element search uses the particle's own element (#223).** When a particle's new position after the diffusion or Stokes step lies in no element, the module puts it on the side its move leaves through. It intersected the move with the triangle of mesh nodes 1 to 3 instead of the particle's own element, moved a particle that had not moved (a move of zero length got a side by coordinate ranges), and returned the side a move starts on whatever the move did next. It now clips the move against the particle's own element. Serial results change for runs with Stokes drift or a random walk (in the Mar Menor Stokes-drift test case 140 of 145 particles end more than 1e-5 degrees from where the old routine put them); runs without either are unchanged.
- **Particles: the next element at a vertex no longer depends on an unseeded random number.** A particle that lands exactly on a mesh vertex is nudged onto one of the two adjacent sides. The side was picked with `random_number`, which the model never seeds, so two serial runs of the same case could give different particle files (measured: the Stokes-drift and the 3D test case differed from run to run; a case whose particles never hit a vertex did not). The pick is now computed from the particle id, the time-step number and the number of element crossings the particle has left in the step, so every run, and later every number of MPI processes, makes the same pick. Results change only for particles that land exactly on a vertex, and those were random before. This is the first stage of the work on particles under MPI (#217), which also adds its test harness: test cases `mm_lgr_a/b/c/e.str`, `lgr_compare.py` (two `.lgr.shy` files compared particle by particle), a debug dump of fluxes, node arrays and particles at `levdbg >= 3` with `lgr_dbg_compare.py`, and the drivers `check_lgr_mpi.sh` and `check_lgr_serial.sh`. On more than one process a particle run no longer crashes at its first output, but it writes no particle records until the output stage of that work.
- **Particles under MPI: the side fluxes are right in elements shared between processes (#217, stage 2).** The particle tracker moves particles with side fluxes that are built node by node. On more than one process a ghost node (a node owned by another process) has only part of its ring of elements, so the fluxes were wrong in every element that holds another process's node: on 4 processes 207 of 315 values in such elements a process owns and 305 of 318 in those it only holds. Each process now adds only the contributions of its own nodes, and the processes that hold a shared element add their partial values together once per step. Measured on 2 and 4 processes for a closed 2D basin, a basin with an open boundary and a river, and a closed 3D basin (surface and bottom layer): no flux differs from the serial run by more than 1e-6 of the largest flux. A serial run is unchanged. Particle runs on more than one process are still not usable: the hand-over of particles between processes, the release and the output are the next stages.
- **Particles: the tracker no longer reads outside its arrays when a particle leaves the domain (#234).** Right after a particle left, through an open boundary or, on several processes, across the edge of a process's domain, the tracker tested the layer count of an element with a negative number. The word found before the array decided whether the particle left or was put back into the element it had tried to leave. On several processes the outcome changed with the contents of memory: the same run of a test case on 8 processes printed 0, 6 or 11 lost-particle messages. With the correction, a plain run and a run with perturbed memory give byte-identical particle dumps. Serial runs: on four test cases (closed 2D basin, basin with an open boundary and a river, closed 3D basin, Stokes drift) the corrected binary writes byte-identical particle files, so in those runs the stray word always meant "leave"; with another mesh or build a particle that should have left may have been kept. Two more reads of the same kind (`iarv` with a negative element number) and three array declarations that were too small for the indices used are corrected on the same path; none of them changed a result. A build with `-fcheck=bounds` now runs the particle test cases to the end, serial and on several processes.
- **Particles on several processes: a run no longer stops when one process has released no particle (#217).** The messages that report a lost particle print a percentage of the particles released on that process. With none released the division stopped the run (test cases on 3 and on 8 processes). The percentage is 0 in that case.
- **Too many MPI processes for a small mesh: one clear message instead of a crash.** When the partitioner leaves a domain without nodes (the 6-node `restart_strip` grid on 3 or 4 processes), the first process died with a floating-point exception while printing the partition table (0/0 for a domain without elements) and the others stopped with `make_domain: no nodes`. The run now prints once that the mesh cannot be split into that many domains, how many would be empty, the mesh size, and `use fewer MPI processes`, then stops every process. The partition table also no longer divides by a zero element count. Runs that worked are unchanged (`restart_strip` serial and on 2 processes, `mm_hyd_00` on 4: outputs byte-identical). Closes #218.
- **An MPI run with a tilted open boundary says why it stops.** Boundary tilting (`ktilt`, `ztilt`) works only in a serial run. On more than one process, the Mar Menor cases that tilt (`mm_hyd_11`, `21`, `41`, `42`, `43`) stopped at start-up: the processes that did not hold node `ktilt` printed `tilt node not found`, and the run ended with `error stop ckbnds: general error`. Such a run now prints once that boundary tilting is not supported with MPI and should run on one process or without `ktilt` and `ztilt`, then stops the same way. `init_tilt` already had this check, but the boundary check reached the abort first; its two bare `stop`s are now `shympi_abort_internal`, so they end every process. The `ktilt`/`ztilt` parameter text and `MANUAL.md` mention the limit. Serial runs are unchanged (Mar Menor `mm_hyd_11` and `mm_hyd_41` outputs byte-identical), and so is a run started with `mpirun -np 1`. Closes #215.
- **GOTM runs no longer compute a bottom stress they throw away.** Each GOTM (`iturb=1`) time step computed a nodal bottom stress from `czdef` (an element loop plus one exchange between MPI ranks), took its square root as the bed friction velocity, and then overwrote that value before GOTM used it: GOTM's bed friction velocity comes from the bottom current and the bed roughness. The stress is now computed only for the `levdbg >= 2` debug check, which is the one place that reads it. Results are unchanged: all 20 output files are byte-identical in the Venice smoke test (serial and 4 MPI ranks), Mar Menor `mm_hyd_41` (6 hours) and the 8 channel-benchmark runs.
- **An explicit run that meets a dry element says why it stops.** With explicit water-level weights (`azpar`/`ampar` 0 and 1) a basin with wetting and drying stopped with only `non diag elems /= 0` and matrix indices; in the Venice lagoon test this happens at the first time step. The message now says that the explicit scheme cannot handle drying and to use semi-implicit weights, and stops with `error stop system_assemble: explicit scheme cannot dry`. The `azpar`/`ampar` parameter text and `MANUAL.md` say the same. The scheme itself is unchanged: its direct solve stores only the diagonal, and a dry element needs off-diagonal terms.

### Changed — Docs
- **EUTRO's known limitations are listed in `MANUAL.md`.** The build it needs, the default calibration (`iwcal = 1`, Venice), and four limitations kept for now (owner decision, delegated, 2026-11-20): phytoplankton settles only when `wsphyt` is set, detritus does not settle (the sediment compartment is switched off in the code, so the manual's state count drops from 11 to the 9 water-column states that run), the reaeration air temperature is fixed at 22 °C, and there is no pelagic loading input. They stay until EUTRO is set up for a real site.
- **GOTM stays the recommended turbulence closure for 3D runs.** `MANUAL.md` and the `iturb` parameter text say so again, with the reason: since 8.5.3 the built-in k-epsilon matches GOTM's standard k-epsilon in columns of 3 or more layers, but columns with 1 or 2 layers keep the old wall treatment (about 2.9 times GOTM in the Venice test).
### Changed — CI
- **Fortran CI checks MPI runs, not only that one starts.** The MPI job ran `mm_hyd_00` on 2 processes and looked at the exit status. It now also runs `testcases/examples/mar_menor/check_mpi.sh` on 4 processes: the energy lines of `mm_hyd_01` must agree with the serial run (relative difference at most 1e-4; 5e-6 today), the tilted-boundary case `mm_hyd_11` must stop with its "not supported with MPI" message, a restart must be written and read, and the 6-node `restart_strip` mesh must stop with "use fewer MPI processes" and no floating-point exception. The Venice smoke test (3D, GOTM, wet/dry, heat) must end on 4 processes. A 4-process sweep of all shipped cases on 2026-11-21 found three MPI problems (#215, #217, #218) that no test had exercised.
- **Fortran CI runs the k-epsilon channel benchmark.** `serial-build-and-test` now runs `testcases/examples/channel_turb/run_all.sh` (about 2 minutes), so a return of the old 1.5x near-bed bias or of a 2-time-step oscillation in `iturb=2` fails CI instead of passing the Venice smoke, which only checks that the run ends. `analyse.py` gates every run whose name starts with `keps` and fails when none was analysed (it used to exit 0 with no GATE line for explicit run names).

## [shyfem-ui 0.8.1] — 2026-11-20

Sortable, filterable grids for Job History and the box-model per-year skill
table; a main menu that works from the keyboard, with landmarks for screen
readers; and a more honest band-amplitude table in the box-model tool (the
30–400 day band is split, short observation gaps no longer blank a window, and
a band resting on a single frequency is left out). These changes have been live
on laguna since 2026-11-04. Tagged `shyfem-ui-v0.8.1`.

### Added — shyfem-ui
- **Job History and the per-year skill table are grids you can sort and filter.** Job History (Run page) and the per-year skill table (Box model, Compare tab) now have column sorting and a filter box per column. Progress and duration sort as numbers, and Job History starts newest first. A job that finishes is added to the grid in place, so the sort and filters you chose stay; redrawing the table on every job event would have reset them each time.
- **The main menu works from the keyboard, and the pages have landmarks.** The menu items and the Collapse control were plain `div`s that only a mouse could reach. They are now buttons in the tab order, activated with Enter or Space, and the current page is marked with `aria-current`. The menu is a navigation landmark ("Main"), the page area is the main landmark, and the IBM and Simulation sidebars are named form landmarks, so a screen reader can jump between them.

### Changed — shyfem-ui
- **Box model: the 30–400 day band is split into 30–90 and 90–400 days.** The seasonal cycle dominates the old band's power, so one number could hide two errors that cancel. On the Curonian run, Ventė 2005–08 read 1.04 in the single band; split, it is 1.30 at 30–90 days and 0.80 at 90–400 days.
- **Box model: a few missing observation days no longer blank a whole window.** The band-amplitude table needed every day of the window, so one missing day left the longest and most informative windows without ratios (Nida and Ventė had none for 2001–2014 because of one missing month). Missing observation days are now filled by linear interpolation when they are at most 2 % of the window and no single gap is longer than 31 days. A gap in the model is never filled. The table states what was filled, for example "Nida: 31 of 5113 days interpolated", and the caption gives the rule.
- **Box model: a band that rests on a single frequency is left out.** In a 120–180 day window the 90–400 day band covers one FFT bin, at a period equal to the window length, where the estimate is least reliable. Such a band now shows as a dash; the 90–400 day band needs a window longer than 180 days. The caption explains it.
- **Run page: the empty Job History grid is hidden.** While "No completed jobs" is showing, the empty grid with its headers and filter boxes is not drawn.

## [shyfem-ui 0.8.0] — 2026-11-03

Closes the 2026-10-19 UI review: every one of its findings is fixed, including
session and WebSocket tokens stored hashed (SEC-06; users signed in once more
after the upgrade). Also: Shiny 1.9 (CI and laguna), job status pushed to the
pages instead of polled, work in progress finished cleanly when a tab closes,
boundary lines that cross refused before meshing, STR lists wrapped at SHYFEM's
80-character line limit, and the Curonian Lagoon sample data. Tagged
`shyfem-ui-v0.8.0`.

### Added — shyfem-ui
- **The Curonian Lagoon boundary and isobaths ship as test data.** `testcases/examples/curonian/` holds the lagoon boundary (three polygons with 21 island holes, a 5136-point coastline) and 435 isobath contours (251k points, 0–95 m), both EPSG:3346, 4.5 MB together. The Mesh Builder integration tests that read them (`TestCuronianIntegration`) only ran on a machine that happened to have the files, so the coastline that made Triangle allocate until the kernel killed it had never been meshed in CI; the class now runs there, including the regression test for the line-crossing gate on that coastline. (M-14, 2026-10-19 UI review)

### Changed — shyfem-ui
- **Job status reaches the pages by push, not by polling.** The job queue now publishes every change of a job (queued, running, progress, ended) and each open session is woken once it is idle (Shiny 1.9's `run_once_when_idle`). The Run page's job list, the Ensemble page's member table and the cross-page "job completed / failed / cancelled" notices update the moment a job changes, instead of up to 2 to 5 seconds later, and an idle session no longer lists the jobs from the database every few seconds. The Run page's workflow progress re-renders on the workflow's own changes the same way. A running job's log tail is refreshed with each of its progress batches. A queue whose jobs change in other processes (the Celery queue of server mode) keeps the previous polls.

### Fixed — shyfem-ui
- **A failed run's error message ends with the tool's own last line again.** The job supervisor wrote its own stderr into the job's error log, so a warning it printed while recording the end (a Python `ResourceWarning` at its exit) could land after SHYFEM's `STOP error stop ...` line, and the error shown for the job sometimes lost that line, which names the cause. The supervisor now writes to its own log in the job state folder; it is read only when the supervisor stopped without a result.
- **Closing the tab no longer leaves half-finished work behind.** Shiny 1.9 stops a page's in-progress work when its session ends. A post-processing run, batch or preset now finishes the shyelab run in flight and renames its output before stopping, where it was killed half-way through the file; an ensemble is submitted whole, so no prepared member folder is left without a job and no job is persisted without being started; a project import writes its records together with the extracted files, or removes the folder again.
- **Code clean-up: the Shiny 1.7 download-button shim is gone.** The Mesh Builder and Box-model downloads use `@render.download_button` directly; the environment pins Shiny 1.9.
- **Mesh Builder: boundary lines that cross each other are refused before meshing.** Simplifying every ring of a boundary on its own, or smoothing the coastline, can make the coastline cut through near-shore islands. Triangle accepted such crossing lines, and with quality refinement its mesh never finished: on the Curonian Lagoon boundary it allocated about 23 GB and was killed by the kernel, taking the worker with it. The boundary check now reports `Line A crosses line B near (x, y)` as an error, the Generate step refuses on it, and `triangulate()` refuses before the mesher is called. Rings that only touch at a shared node or lie on top of each other are not crossings; Triangle merges those.
- **STR files: a boundary node list that goes on over several lines is read whole, also when its first line holds one node.** `kbound = 1547` followed by a line `1548 1549` is one three-node boundary to SHYFEM, but the UI only continued a list that already had two numbers on its first line, so the Boundary editor showed the boundary with only node 1547, and a Generate wrote it back with the other nodes gone. The continuation lines are now part of the list, and a list written back goes on over several lines the same way: SHYFEM stops on an STR line longer than 80 characters, and a long node list written on one line (the Boundary editor's Generate, or an edit of any list parameter in the STR editor) did exactly that. A text value that cannot fit on one line is refused with a message instead of written. (S-11, 2026-10-19 UI review)
- **STR editor: the `$title` lines stay text.** A title containing `name = value`, such as `strip mesh restart (nkn=6 > nel=4)` in the shipped restart test case, was read as parameters `nkn` and `nel`; the STR editor showed them as fields, and an Apply rewrote the title line. `$title` (title, run name, basin) is now read as text only, as SHYFEM reads it.
- **Grid Prep and Mesh Builder quality statistics: a four-node element whose first node is node 3 no longer counts as a triangle.** A workaround for an old grid-reader fault took any element listed as `3, a, b, c` for the triangle `a, b, c`, so such a quad entered the quality, area and angle statistics as a wrong triangle. The grid reader has not produced that shape for a long time; the workaround is gone and quads are left out like other non-triangles. (M-13, 2026-10-19 UI review)
- **Simulation page, Boundary editor: a `zfact = 1.0` from the file is kept, and a value that is not a number no longer closes the session.** The editor wrote `zfact` only when it differed from 1.0, so a Generate dropped an explicit `zfact = 1.0` (and a cleared field kept the old value). It now writes `zfact` whenever it is set and leaves it out when the field is empty. A `$boundN` whose `ibtyp`, `zfact` or `intpol` is not a number (`ibtyp = level`) raised in a reactive effect and ended the session on load; the editor now says which section and parameter it could not read and shows no boundaries. A Scale factor field that is not a number stops Generate with a message, where it used to keep the old value silently. Generate pressed before a just-added, imported or reloaded boundary card had reported its fields did nothing at all; it now uses that card's stored values. `nan` and `inf`, which Python reads as numbers and SHYFEM does not, are refused the same way.
- **Partitioning tests check the real shyparts command.** Two tests still required the `-weighted` option that the Partitioning page used to send and shyparts does not have; they would have passed again had the broken option come back. They now check the command shyparts accepts (`-np N grid`, extra options first) and that the real shyparts refuses `-weighted`. No change to the page. (M-15, 2026-10-19 UI review)
- **Mesh Builder Step 2: the chosen line and smoothing settings stay after Apply.** Every Apply Smoothing, Apply Simplification or Reset redrew the whole panel, so the line choice went back to "All lines" (the next Apply then changed every line, not the one picked) and the method, iterations and tolerance went back to their defaults. Now only the line list is redrawn, to show the new point counts, and it keeps the chosen line. A new import starts at "All lines" again: the kept choice used to carry over to the next boundary's line of the same number.
- **Box-model: a cache rebuilt by another session reaches the page without re-selecting the run.** The page only watched builds it had started itself, so after a rebuild from another browser tab it kept showing the old build until the run was picked again, and an output-step (hourly) window read from disk could be paired with the old build's metadata. The page now checks every 10 s whether each run's published cache changed (one `stat` of its `meta.json`) and reloads it if so. A load re-reads a cache that was republished in the middle of the read, so every file it shows comes from the same build. An hourly window that sees the cache change while it is read says so ("the cache was rebuilt since it was loaded; refreshing") and is not shown. (B-04, 2026-10-19 UI review)
- **Box-model: two publishes of the same finished build can no longer lose the cache.** When a build finished, its own worker and a page load elsewhere (another worker, or another session once the cache readers run in the background) could both try to publish it; the second could move the freshly published cache aside and then have nothing to put in its place, so the run showed no cache and its files were swept away as leftovers. Publishing now takes a lock file in the cache folder, so the second publisher waits, sees the build is already published, and leaves it alone. (B-05, 2026-10-19 UI review)
- **Box-model: opening a run no longer freezes everyone else's page.** The page read its Parquet cache (the selected run, every run of the Compare tab, and the output-step window) on the one event loop that serves every session, so while a large cache loaded, every other user's page stopped responding. Those reads now run in the background; the page shows the result once it is read, and a read that lands after you picked another run is never shown for the new one. (B-06, 2026-10-19 UI review)
- **Box-model Setup map: section interfaces sit on the box boundaries of a projected grid.** SHYFEM writes the section nodes in the grid's own coordinates, and the Setup map drew them as longitude/latitude, so on a grid in metres (UTM, Gauss-Boaga) the interface lines landed far away from the box outlines. They are now converted with the same coordinate system as the box outlines; a projected grid whose coordinate system cannot be worked out draws no interface lines rather than misplaced ones. Geographic grids such as the Curonian ones are unchanged. (B-01, 2026-10-19 UI review)
- **Box-model: a cache build is refused once the project is at its storage quota.** The cache counted towards the project's storage quota but builds never checked it, so a project already at its limit could keep growing with every new run's cache while uploads were refused. Building a cache now says how much of the quota is used and asks you to free some space first. Rebuilding a run is not charged for the cache it replaces, so a stale cache can still be refreshed. (B-02, 2026-10-19 UI review)
- **A PostgreSQL database can be used again.** The app handed the database migrations its connection address with the password replaced by `***`, so with the documented PostgreSQL setup the app could not start (the SQLite database used on laguna has no password and was not affected); a password with a percent-encoded character also stopped the `alembic` command. The migrations now get the real address; the password still never appears in the logs. (D-01, 2026-10-19 UI review)
- **A cancelled workflow says Cancelled, and stops.** A workflow cancelled from another browser session than the one that started it (an admin, or the owner after reloading the page) was shown as Failed with "Step … failed: Job was cancelled", and a cancel that landed between two steps was undone: the workflow went back to Running and started its next step. It is now recorded as Cancelled and no further step starts, and a cancel that lands while a step's job is still being started stops that job too instead of letting it run to the end; a step job cancelled on its own also marks its workflow Cancelled. (J-05, 2026-10-19 UI review)
- **A job's "Created" time is local time again.** Jobs loaded from the database (after a restart, or once a run finished) showed their creation time in UTC, three hours before "Started" in a Lithuanian summer, and a reloaded waiting job's elapsed time was off by as much. The creation time is now shown in the server's local time like the job's other times. (J-09, 2026-10-19 UI review)
- **Feedback is kept for its full retention time.** The clean-up that deletes old feedback compared the UTC time each report was saved with the server's local clock, so on laguna (UTC+2/+3) it deleted feedback two to three hours before it reached the retention age. It now compares UTC with UTC. (D-05, 2026-10-19 UI review)
- **A finished job's output files are kept in the database with a Celery queue.** In server mode with the Celery job queue, the database record of a finished job never got the list of files the run produced (the local queue used on laguna does save it), so the record said the run produced nothing, and the list was lost with the Redis job store (for example after a Redis restart without persistence). The worker now saves it with the job's other results. (J-12, 2026-10-19 UI review)
- **A slow Redis no longer freezes the app with a Celery queue.** In server mode with the Celery job queue, submitting, cancelling, listing and polling jobs and reading a job's log talked to Redis on the thread that serves every browser session, so while Redis was slow or unreachable (up to 10 s per request) the whole app stopped responding for everyone; the Run page polls every 2 s. These calls now run in the background and only the page waiting for them waits. (J-11, 2026-10-19 UI review)
- **Running an ensemble again no longer overwrites the previous one.** Submitting an ensemble under a name (or working directory) already used put its runs in the earlier ensemble's run folders: its input files were copied over the old ones and the new runs overwrote the earlier results, or wrote into them at the same time if that ensemble was still running. The Ensemble page now stops before creating or starting anything and asks for another name or working directory (or for those folders to be removed first); empty folders and a fresh name work as before. (R-08, 2026-10-19 UI review)
- **Code clean-up: an unused pre-run file check is gone.** A check that the files named in a run's STR exist on disk had no caller, so it never ran for anyone, while its tests suggested runs were being checked; it and its tests are removed (the Run page's STR parameter check is unchanged). (F-11, 2026-10-19 UI review)
- **Files: a failed save no longer leaves the disk and the file list out of step.** An upload wrote the file before its database row; when the row could not be saved the file stayed on disk, unlisted and outside the storage limit (and a re-upload had already overwritten the earlier version). Deleting did the reverse: the file went first, so a failed save left a listed file that no longer existed. Now a failed upload removes the new file or puts the earlier version back, and a delete removes the row before the file. (F-04, 2026-10-19 UI review)
- **Files: uploading into the subdirectory `.` no longer lists the file twice.** A `.` (or `./`) subdirectory was stored as `./name`, a second entry beside `name` for the same file on disk, counted twice against the storage limit; it now means the project folder itself. (F-08, 2026-10-19 UI review)
- **Files: a refused upload now says why.** Whatever stopped an upload (the project's storage limit, an invalid file name, a name reserved for job logs, a bad subdirectory), the Files page showed only "Failed to upload: name"; it now adds the reason, and an unexpected error says the file could not be saved without showing server paths. (F-09, 2026-10-19 UI review)
- **Server start: the tutorial account no longer gets someone else's project.** At every start the app looked for its shared Mar Menor tutorial project by name only, so a user's own project called "Mar Menor Tutorial" was taken for it and shared, with edit rights, with the tutorial account; and once an admin renamed the tutorial project, a second one was added on the same folder. It now finds the admin's tutorial project by its folder, and if a project of another owner holds the name or the folder it shares nothing and logs a warning. (H-09, 2026-10-19 UI review)
- **Operators: moving old projects into their owners' homes leaves a project with a running job alone.** The relocation (`relocate_legacy_projects`, `scripts/migrations/relocate_projects_to_user_homes.py --apply`) moved every project folder without looking at jobs, so a run still in progress lost its folder: its outputs and logs went to a path that no longer existed. A project with a job that is pending, queued or running, or a workflow that is pending or running, is now left where it is and named in the log; run the relocation again once it has finished. (H-10, 2026-10-19 UI review)
- **Compare: "Generate Comparison Report" saves the report in your project.** It wrote the HTML into the server's shared work folder, which in server mode is outside every user's home, so it was out of reach of your own project and pickers, and everyone's reports went into the same folder. The report now goes in the active project's folder, the message names the file without the server path, and writing it no longer holds up the page. (V-08, 2026-10-19 UI review)
- **A copy of the database can no longer be used to sign in.** The database kept every sign-in session's token, and the token linking a page's live connection to it, exactly as the browser holds them, so anyone who could read the database file (a backup, a copied file) could put one in a browser and be signed in as that user until the session ran out. The database now keeps only a one-way fingerprint (SHA-256) of each token, which cannot be turned back into it; signing in, signing out and the page's connection work as before. Sessions stored before this change are removed when the database is upgraded, so anyone signed in at that moment signs in again (SEC-06, 2026-10-19 UI review).
- **Request ids in the logs can no longer be forged or made huge.** The app took any `X-Request-Id` header a browser sent, echoed it back and wrote it into every log line of that request, so a client could send a 10 000-character id, or one with line breaks or brackets that faked extra log lines. Only a short plain id (letters, digits, `.`, `_`, `-`, at most 128 characters) is now kept; anything else is replaced by a fresh id (SEC-07, 2026-10-19 UI review).
- **A file path starting with `~` is now refused plainly.** On the server a path like `~someone/x` was expanded to that host account's home: an unknown name raised an internal error that the pages did not catch, and a known one (`~root`) was rejected with a message printing the server folder, so the two answers told apart which accounts exist on the server. Such paths, and `~/...` on the server, are now refused with one message that names no server folder; on a local desktop install `~/...` still means your home. Any other refused path, such as `/etc/x` or `../../x`, was also reported with the full server path and your home folder (or every allowed folder); on the server such messages now name only the file (or `~/...` inside your home) and no server folder (SEC-08, 2026-10-19 UI review).
- **Admin, Audit log: sharing a project and removing someone's access are now recorded.** Every user-management action on the Admin page went into the audit log, but giving a user viewer or editor access to a project, or taking it away, left no trace, so an admin could not see who had opened a project to whom. Both now write an entry with the user who did it, the project, the other user and the role (SEC-05, 2026-10-19 UI review).
- **Admin, Audit log: a start-up role change is now recorded.** At every start the app forces the configured tutorial account back to the tutorial role (on purpose, so accounts made before that role existed get it), but it did so silently: if that name belonged to someone who had been given another role, they were quietly reset with no trace. The reset still happens; it now writes a warning to the server log and a `role_reforced` entry to the audit log naming the account and both roles (SEC-03, 2026-10-19 UI review).
- **Rate limit and audit log: a garbled forwarded address no longer becomes a client's address.** When the app is behind a trusted proxy and a request's `X-Forwarded-For` header held only entries that are not IP addresses, the app took the first such text (for example `garbage`) as the client's address, so every client sending it shared one sign-in rate-limit bucket and the audit log recorded that text instead of an address; the test meant to catch this checked only that some text came back. Unparseable entries are now skipped and, if none is left, the connecting address is used. Behind laguna's nginx, which always appends the real address, nothing changes. The tests for this, for the `Secure` flag on the sign-in cookie and for creating the start-up accounts now check the actual result (SEC-10, 2026-10-19 UI review).
- **Dashboard: the project buttons stay clickable, and act under the right name.** A long project folder path did not wrap, so it widened the projects table until Load, Details, Export and Clone ran under the Quick Start card, which then took every click on them; the path now wraps and the table scrolls inside its card. And after a project was deleted, a new project that got the same id was cloned, exported and shared under the deleted project's name in the same session (the Export ZIP was named after it); they now use the current name.
- **Visualize: the NetCDF data type is now "SHYFEM results", and it shows the results.** It opens a `.shy` file (converted once with shyelab and cached in your home, or the work folder when run locally, so the next load is immediate) or SHYFEM NetCDF, and shows the variable on the mesh map with a time slider, play/pause, a legend and, for a file with currents, optional current arrows. It replaces the plot that failed with "list index out of range" on every SHYFEM NetCDF file. The Vertical Profile and Comparison tabs say they are not available for SHYFEM results yet; Statistics shows the colour range of the variable on the map and the units of all variables. A Load that fails (a conversion error, or a file that is not a results file) says so and keeps the file already on the map. (V-01, 2026-10-19 UI review)
- **Jobs, local queue (the production default): a run no longer dies when the last browser tab closes.** Shiny Server stops an idle worker 5 s after its last connection, and the job ran inside that worker, so the shutdown killed `shyfem`/`mpirun` and recorded "Job was cancelled", with no email. A run only survived while some session kept the worker alive. Each job now runs under a small supervisor process (`python -m shyfem_ui.job_runner`) in its own session. The supervisor writes the tool's output straight to the job's `.stdout`/`.stderr` files, records the exit status, and ends the job's row and sends the email itself, even when no worker is running. The worker only watches the files; a worker stopping leaves the run alone. A user's cancel still kills the run. The supervisor's bookkeeping sits next to the logs as `<job>.job`, `<job>.pid` and `<job>.exit`; it is left out of exports and removed with the job. (J-01, 2026-10-19 UI review)
- **Jobs, restart:** a worker that starts while jobs are running watches them again instead of marking them "orphaned at server restart". This also covers the `restart.txt` overlap, where the previous worker is still serving (J-08). A job whose supervisor left an exit record but died before ending the row is reported from that record. Only a job with no live supervisor and no record is marked orphaned.
- **Runs and tools that stopped on an error no longer report success.** gfortran's `stop 'message'` exits with status 0, and the UI used the exit status alone, so a missing basin, an STR line over 80 characters, an end time before the start, or a flag a tool does not have all showed as COMPLETED or "completed successfully". A run now also fails when its output contains `STOP error stop`, `*** no such option` or `STOP clo_usage`, or, for shyfem, when it never printed its `simulation end:` line. The failure message names the line that stopped it. This covers jobs, workflows and the tool pages (Grid Prep, Partitioning, Post-process, Mesh Builder). Under `mpirun` only errors after MPI start-up exited non-zero before; STR and basin errors did not. (X-01, 2026-10-19 UI review)
- **Physics page: Save no longer changes physics nobody edited.** Panels showed `value or default`, so an explicit `0` showed as the default (`ilin = 0` as 1, `aapar = 0.` as 1.0, also `albedo`, `zfact` and others), and Save wrote every shown value back. A save with no edit therefore turned `ilin = 0` into `ilin = 1` (20 shipped STRs have `ilin = 0`) and added absent parameters at their defaults. Save now writes only the fields whose value differs from what the panel showed. An untouched parameter keeps its value and spelling, and an absent one stays absent; the meteo-output checkboxes (`imetout`) and the assimilation blocks follow the same rule. A select whose stored value is not one of its options (`iclin = 1.`, shown as "1.0") no longer shows the first option, which Save wrote back (`iclin = 0`). Every panel now re-renders on Load and Save, even while collapsed; a collapsed panel kept the previous file's values and Save wrote them into the new one. With every panel open and no edit, every shipped testcase STR saves back byte-identical. A panel that cannot show the loaded file (for example `vismol = 1.d-6`) now says so, and Save skips its fields; before, it kept the previous file's values and Save wrote them in. `idtsyn` and `idtlgr` are now text fields, because shipped STRs write them as intervals (`'1h'`), which broke the Hydrodynamics and Lagrangian panels for 23 of them. (S-01, 2026-10-19 UI review)
- **Physics page, Boundary Conditions:** opening the panel and saving no longer appends an unnumbered `$bound` section. The core stops on that section (`bnd: ibc out of bounds`). The panel cannot write `$bound1`, `$bound2`, … so an edit there is refused with a message pointing at the STR editor. The Physics page and the STR editor's Validate both reject an unnumbered `$bound`, and the editor's "insert section" template now inserts `$bound1`. (S-02)
- **Physics page, Lagrangian panel:** opening it and saving no longer writes `ilagr` into `$para`. `ilagr` belongs to `$lagrg`, and the core stops on it in `$para` (`nls_insert_variable: wrong section`), so the saved STR could not run.
- **Physics page:** `idtcon` and `icon_av` appear in two panels, and the copy that was not edited no longer overwrites the edited one. When the two copies hold different edits, the save is refused (S-08). Restart mode `ityrst` and boundary `intpol` now default to 0, the core's default (they were 1). The `intpol` choices are now the core's: 0 auto, 1 stepwise, 2 linear, 4 cubic (S-10). Text fields show a run of numbers (`sedgrs = 0.1 0.2 0.3`) as written, not as `[0.1, 0.2, 0.3]`.
- **Files: "Seed Tutorial Files" no longer overwrites a project's files.** Imported, cloned and new tutorial projects got no file rows, so the Files page listed nothing, showed 0 B, and offered the seed button; seeding then copied the tutorial over same-named files such as an edited `mm_hyd_00.str`. Seeding now refuses any project that has a file row or a project file on disk, and the button shows only for an empty project. Import, clone and the new Mar Menor tutorial project now register a row for each project file (the same files an export ships), so they are listed and count against the project storage limit; an import or clone over that limit is refused. This counts everything copied, run outputs included, which a project's own runs do not add to its usage, so a large project with big outputs may now be too large to clone. Import no longer extracts job logs and bookkeeping files (`.stdout`, `.stderr`, `.job`, `.pid`, `.exit`, `.project_summary.json`); they got no row, so they used disk space the limit did not see. A file type the user chose (for example `boundary`) now survives export, import and clone. Projects created before this fix still have no rows. (F-01, 2026-10-19 UI review)
- **Mar Menor tutorial project: the name no longer chooses where the copy lands.** The typed name was joined to the shared work folder and the tutorial copied there, so a name such as `../../somewhere` or `../users/<other user>/x` put a copy outside the work folder or in another user's home; any signed-in account could do it. The name must now be one plain folder name, without `/`, `\` or a leading `.`; anything else is refused with a message, not rewritten. In server mode the project now goes in its owner's home like other new projects. Before, it went in the shared work folder, where its owner's file pickers could not reach it. A folder or link that already has the name is refused, not followed. (H-03, tutorial half of F-02, 2026-10-19 UI review)

## [8.5.2] — 2026-10-18

A core fix release. The main fix changes results for every 3D run with a
flux (`ibtyp=2`) or point-source (`ibtyp=3`) boundary, such as a river,
made since 2026-02-11. The vertical velocity had been zeroed at those
nodes, which broke their vertical mass balance; some runs blew up at the
source. GOTM also takes its bottom roughness from `czdef` under
`ireib=6`. Tagged `v8.5.2`.

### Fixed
- **Model, 3D flux and point-source boundaries (changes results for 3D runs with `ibtyp=2` or `ibtyp=3` boundaries since 2026-02-11):** the vertical velocity is zeroed only at level boundaries (`ibtyp=1`) again, as upstream does after its 2010 fix for `ibtyp=2`. Commit `4ae5c575` (shipped in #5) zeroed it wherever `iopbnd(k) > 0`, which is every boundary node, flux and point-source nodes included. Those boundaries enter as nodal volume sources that have to close through w, so the change broke the vertical mass balance there. In `mar_menor`, `mm_hyd_41`, `42` and `43` ran away at the river node within 4–5 hours (salinity 88, temperature 100 °C) on every version since. They run their full period again, and the CI battery is unchanged. Found by bisecting from v8.1.1, where the case ran.
- **Model, GOTM turbulence (changes results for `ireib=6` runs with `iturb=1`):** GOTM's bottom roughness length is now the one the momentum friction uses under `ireib=6`: an area-weighted node average of each element's roughness (`czv`, from `$area`, `czdef` by default). It used to be `z0bk`, which only the fluid-mud option (`ireib=9`) sets, so it stayed at the initial 0.9 mm whatever `czdef` said. The effect is negligible with GOTM's default Neumann wall conditions: no measurable change in the `channel_turb` benchmark. No shipped test case uses `ireib=6`; `venlag_smoke` and `mm_hyd_00` are byte-identical. (k-ε vs GOTM benchmark, decision 4)


### Changed
- **Turbulence, documentation:** GOTM (`iturb=1`) is recommended over the built-in k-epsilon (`iturb=2`) for 3D runs. In the `channel_turb` benchmark, `iturb=2` gives 1.5x the log-law eddy viscosity near the bed, against GOTM's roughly 0.8x (`docs/reviews/2026-10-18-keps-vs-gotm-benchmark.md`; redesign tracked in #125). A 3D run with `iturb=2` prints a start-up warning saying so, and each shipped `gotmturb.nml` now has a header saying which closure it configures. (#124, #126)

## [shyfem-ui 0.7.2] — 2026-10-18

Server (Celery) mode: a cancelled job now ends cancelled. Tagged
`shyfem-ui-v0.7.2`. The default local job queue is unchanged.

### Fixed — server (Celery) mode
- **Cancel:** a cancelled job reappeared as "running" after the cancel, and the lost-job reconcile later labelled it "lost". Cancelling revokes the task, which makes Celery stop the worker process with `SystemExit`. The run itself was stopped, but the task's cleanup wrote the job's old RUNNING status back over the cancel. It now records CANCELLED, in Redis and in the database, and sends no email. (#122)
